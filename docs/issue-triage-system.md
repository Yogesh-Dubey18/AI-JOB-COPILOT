# Issue Triage System

## Intake Sources

- In-app feedback page.
- Admin feedback dashboard.
- Demo tester notes.
- GitHub issues.
- Recruiter or mentor review notes.

## Priority Rules

- High: privacy risk, security concern, data loss, blocked core flow, broken auth, broken resume upload, broken application tracking.
- Medium: confusing AI output, inaccurate analysis, UX friction in a core workflow, slow but usable feature.
- Low: copy improvements, nice-to-have polish, additional templates, non-critical layout improvements.

## Triage Steps

1. Read the feedback and remove private details from the working issue.
2. Confirm whether it is a bug, feature, documentation update, or research item.
3. Generate or write a GitHub issue draft.
4. Add labels and a release target only when the work is scheduled.
5. Link the issue back to the feedback record if an issue URL exists.
6. Close feedback only after the issue is shipped, rejected with a clear reason, or moved to a tracked backlog item.

## Weekly Review

- Review open high-priority feedback first.
- Group repeated feedback into one issue.
- Convert only actionable items into implementation work.
- Keep commercial/legal feedback as professional-review tasks.
